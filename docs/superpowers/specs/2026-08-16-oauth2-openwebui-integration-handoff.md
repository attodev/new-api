# OpenWebUI-Side Integration Contract (new-api OAuth2 Provider)

> Handoff document for the team rebuilding the OpenWebUI-side integration.
> This describes only what that side needs to implement to talk to
> new-api's OAuth2 provider. See
> `2026-08-16-oauth2-provider-design.md` for the new-api-side design.

## Why this replaces the original "generic OIDC" plan

The original proposal was to point OpenWebUI's existing generic-OIDC login
client at new-api, reusing that code unmodified. That assumed OpenWebUI
would be the party that *initiates* the login by redirecting the browser to
new-api's `/authorize` endpoint.

That doesn't work here: new-api's session cookie is `SameSite=Strict`, so a
top-level browser redirect arriving from another origin (OpenWebUI) would
not carry the user's new-api session cookie, and the "user is already
logged into new-api" check would fail even though they are logged in.

Instead, new-api itself initiates the hand-off from a page the user is
already on (same-origin, cookie present), and hands the browser a link
straight to an OpenWebUI callback with an authorization code already
attached. **This means OpenWebUI needs a small custom callback route, not
a drop-in OIDC provider configuration.**

## 1. New callback route

Add a route, e.g.:

```
GET /auth/newapi/callback?code=<code>&state=<state>
```

new-api links directly to this URL (e.g. from a "Open in Chat App" button
in its playground). `state` is generated by new-api and passed through
opaquely — OpenWebUI does not need to have set it beforehand and does not
need to validate it. The security property here comes from `code` being
single-use and short-lived (120 seconds), not from `state`.

## 2. What the callback handler does

All of the following are server-to-server calls made by OpenWebUI's
backend — no browser cookies or CORS involved.

### a. Exchange the code for an access token

```
POST https://<new-api-host>/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
code=<code from the callback query string>
client_id=<provided by new-api ops>
client_secret=<provided by new-api ops>
```

Success response (`200`):
```json
{
  "access_token": "sk-xxxxxxxx",
  "token_type": "Bearer",
  "expires_in": 86400
}
```

Error responses:
- `400 {"error": "invalid_grant"}` — code expired or already used. Show the
  user an error and ask them to click the link again from new-api.
- `401 {"error": "invalid_client"}` — `client_id`/`client_secret` mismatch.
  This indicates a configuration problem, not a per-user error.

### b. Fetch user identity

```
GET https://<new-api-host>/oauth2/userinfo
Authorization: Bearer <access_token>
```

Response (`200`):
```json
{
  "sub": "<new-api user id, stable>",
  "email": "<user email>",
  "name": "<user display name>"
}
```

`401` if the access token is invalid/expired — shouldn't happen immediately
after a fresh exchange, but handle it the same way as an expired session
(see section 4).

### c. Map to a local OpenWebUI account and establish a session

Look up or auto-create a local OpenWebUI user keyed by `sub` (fall back to
`email` if needed), then issue OpenWebUI's own normal session/cookie for
that user exactly as its existing auth system does today. This part is
unchanged from how OpenWebUI already handles first-time account creation
for any external login method.

### d. Store the access token as this user's per-session connection credential

This is the part that makes per-user billing work, and it's required
regardless of how the browser got here:

**OpenWebUI's OpenAI-compatible connection must use *this* user's
`access_token` as the `Authorization: Bearer` value for that user's chat
requests — not a single shared admin API key.** Concretely, requests to:

```
POST https://<new-api-host>/v1/chat/completions
GET  https://<new-api-host>/v1/models
```

(and any other relayed endpoint) must carry
`Authorization: Bearer <that user's access_token>`, sourced from the
session established in step (c), rather than a global connection-level key
configured by an admin. Every place in OpenWebUI's code that currently
reads a fixed admin key for the OpenAI connection needs to instead resolve
the current request's user and use their stored `access_token`.

Persist `access_token` and its expiry (`issued_at + expires_in`) alongside
the OpenWebUI session so it can be checked before use.

### e. Redirect to the normal post-login landing page

Once OpenWebUI's own session cookie is set, redirect the browser to
wherever a normal login completes today (e.g. `/`).

## 3. Token expiry — no refresh token

- `access_token` is valid for `expires_in` seconds (currently 86400 = 24h)
  from issuance.
- **There is no refresh token.** When it expires, calls to new-api will
  start returning `401`.
- Logging out of new-api also invalidates the token immediately (before the
  24h mark) — same `401` behavior.

OpenWebUI must detect a `401` from new-api on a relayed request and show
the user a clear "reconnect" prompt (e.g. "Your connection to \[new-api\]
has expired — click here to reconnect") that sends them back to new-api's
own UI to click the connect link again, producing a fresh code and a fresh
`access_token`. This should not look like a generic error — users will hit
this roughly once a day in normal use.

## 4. What NOT to build

- Do not configure this through OpenWebUI's existing generic-OIDC provider
  settings screen — that flow assumes OpenWebUI initiates the redirect,
  which doesn't apply here (see section "Why this replaces..." above).
- No PKCE, no refresh token, no consent screen to build — none of these
  exist on the new-api side for this integration.

## Values to be provided by new-api ops before implementation

- `client_id`
- `client_secret`
- New-api host / base URL for the three endpoints above
- The exact callback URL to register with new-api (`https://<openwebui-host>/auth/newapi/callback` or whatever path is chosen) — new-api's `redirect_uri` system setting must match this exactly, or the flow will be rejected at code-issuance time.
