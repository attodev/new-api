# 사용자 잔액 캐시 상주 설계

작성: 2026-10-15. 상태: 검토 대기. 대상 브랜치: `develop` (worktree `/Users/molla/work/ai/new-api-rebase`).

## 1. 목적

배치 업데이트(`BATCH_UPDATE_ENABLED=true`)를 켠 develop에서, 사용자 지갑 잔액이 실제보다 많이 쓰여 최종 잔액이 음수가 되는 문제를 없앤다. 요청을 막지 않고, DB로 우회하지 않으며, upstream의 인증 장치(인증 버전 fence, 세션 캐시)는 지금 동작을 그대로 둔다.

## 2. 배경

### 2.1 지금 develop의 동작

- 사용자 캐시는 Redis 해시 `user:<id>` 하나다. 인증 정보(그룹, 상태, 역할, 인증 버전 등)와 잔액(`Quota`)이 함께 들어 있다.
- 해시의 TTL은 `SYNC_FREQUENCY`(기본 60초)이고, 처음 채우거나 다시 쓸 때만 설정된다. 사전 차감(`userQuotaReserveScript`)과 정산(`userQuotaDeltaScript`)은 TTL을 건드리지 않는다. 그래서 계속 쓰이는 사용자도 60초마다 해시가 사라진다.
- 해시가 없으면 `TryReserveUserQuota`가 `GetUserCache`로 DB 행을 읽어 해시를 다시 채운다(`model/quota_reserve.go`, `model/user_cache.go`).
- 배치 모드에서 차감은 Redis에 먼저 반영되고, DB에는 `BATCH_UPDATE_INTERVAL`(기본 5초)마다 배치로 반영된다. 운영 환경(AWS)에서는 배치의 DB 쓰기가 3~5초까지 걸린다.

### 2.2 재현 결과

develop에서 miniredis 테스트로 재현했다. 잔액 1000에서 100을 차감하고, 배치 반영 전에 해시를 지운(만료) 뒤 다시 100을 차감했다.

| 단계 | DB | 캐시 |
|---|---|---|
| 해시 재생성과 배치 반영 직후 | 800 | 900 |
| 캐시 잔액 900을 모두 쓴 뒤 배치 반영 | -100 | 0 |

해시가 사라진 순간 DB에 반영되지 않은 차감분(여기서는 100)이 캐시에서 사라지고, 그만큼 초과 사용이 가능하다. API 키 캐시(`token:<hmac>`)도 같은 결과(DB 800, 캐시 900)였다.

### 2.3 원인

해시가 사라지는 가장 흔한 원인은 메모리 부족이 아니라 60초 TTL이다. 메모리는 사용자당 수 KB 이하라(§7) 키가 밀려날 가능성은 사실상 없다. 따라서 쓰는 동안 잔액 해시가 사라지지 않게 하면 구멍이 닫힌다.

## 3. 결정 사항

1. 사용자 잔액 캐시를 Redis에 상주시킨다. 잔액 TTL 기본값은 24시간(86400초)이다.
2. 잔액 외 사용자 정보는 지금과 같은 주기로 DB에서 다시 읽는다. 단, 요청이 들어온 순간에만 확인한다(백그라운드 작업 없음).
3. 요청을 막는 방식(team `10ade7045`)은 쓰지 않는다. 캐시 miss 때 DB로 우회해 차감하는 방식도 쓰지 않는다.
4. API 키 캐시는 바꾸지 않는다(§6에 남는 한계로 기록).
5. 조직 기능이 캐시를 지우는(`InvalidateUserCache`) 경로는 바꾸지 않는다.
6. 캐시와 DB 잔액이 어긋난 것을 자동으로 보정하지 않는다. 감지해서 로그만 남긴다.
7. 앱 서버는 HA 구성으로 여러 대가 같은 Redis를 쓸 수 있다고 가정한다. 배치 대기분은 서버마다 프로세스 메모리에 있으므로, 어긋남 판정은 이 가정에서 성립하는 규칙(§4.7)을 쓴다.
8. `team` 브랜치는 이 작업의 범위가 아니다.

## 4. 설계

### 4.1 두 개의 시계

| 시계 | 위치 | 기본값 | 연장되는 때 | 하는 일 |
|---|---|---|---|---|
| 잔액 TTL | Redis 키의 EXPIRE | 86400초 | 잔액이 바뀔 때만(사전 차감, 정산, 충전 등 캐시에 차이를 더하는 모든 경로) | 0이 되면 Redis가 해시를 지운다 |
| 정보 신선 기한 | 해시 필드 `FreshUntil`(unix 초) | 쓰는 시각 + `SYNC_FREQUENCY` | 사용자 정보를 DB에서 다시 읽어 쓸 때 | 요청이 해시를 읽을 때만 확인한다. 지났으면 사용자 정보를 다시 읽는다 |

- 신선 기한은 Redis TTL이 아니다. 혼자서는 아무 일도 하지 않는다.
- 사용자 정보를 다시 읽는 동작은 잔액 TTL을 연장하지 않는다.
- 사용하지 않는 사용자는 마지막으로 잔액이 바뀐 뒤 24시간이 지나면 Redis가 해시를 지운다. 그 시점에는 그 사용자의 차감분이 모두 DB에 반영돼 있으므로, 다음 요청에서 DB 잔액으로 다시 채워도 정확하다.

### 4.2 잔액 TTL 연장

- 사용자 사전 차감 스크립트와 정산(delta) 스크립트는 `HINCRBY`가 성공한 경우에만 `EXPIRE <잔액 TTL>`을 함께 실행한다. 잔액 부족으로 거절한 경우와 해시가 없는 경우는 TTL을 건드리지 않는다.
- 같은 스크립트를 쓰는 다른 경로(`cacheIncrUserQuota`, `syncCreditUserQuotaCache` 등)도 자동으로 같은 규칙을 따른다.

### 4.3 사용자 정보 다시 읽기

읽기 경로(`cacheGetUserBase` → `GetUserCache`)를 다음처럼 바꾼다.

1. 해시를 읽는다. 지금 하는 검사(스키마 버전, 인증 버전 floor)는 그대로다.
2. `FreshUntil`이 없거나 지났으면 "정보가 오래됨"으로 보고, 지금의 miss 처리와 같은 경로로 DB 행을 읽어 해시에 쓴다.
3. 이때 잔액은 덮어쓰지 않는다. 지금 캐시 쓰기 스크립트(`writeUserCache`)의 "Quota 필드가 이미 있으면 쓰지 않는다" 규칙을 그대로 쓴다.
4. 호출자에게 돌려주는 `UserBase`의 `Quota`는 DB 값이 아니라 캐시에 남아 있는 잔액이어야 한다. 이 값은 `ContextKeyUserQuota`를 거쳐 relay의 `UserQuota`로 쓰인다(`relay/common/relay_info.go:623`). 쓰기 뒤 해시를 다시 읽어 돌려주는 방식으로 맞춘다.
5. 인증 fence가 걸려 있어 쓰기가 거절되면(`ErrUserAuthCachePending`) 지금과 똑같이 처리한다.

### 4.4 캐시 쓰기 규칙

`writeUserCache` 스크립트의 동작을 다음처럼 정한다.

| 상황 | 필드 | `Quota` | `FreshUntil` | EXPIRE |
|---|---|---|---|---|
| 해시가 없음(새로 채움) | 모두 씀 | DB 값으로 씀 | 지금 + `SYNC_FREQUENCY` | 잔액 TTL로 설정 |
| 해시가 있음(정보 다시 읽기) | 모두 씀 | 그대로 둠 | 지금 + `SYNC_FREQUENCY` | 그대로 둠 |

- 인증 버전 비교, fence 확인, committed floor 갱신 같은 지금 스크립트의 나머지 규칙은 바꾸지 않는다.
- 필드 개별 수정 스크립트(`updateUserCacheFieldAtVersion`)는 이미 EXPIRE를 건드리지 않으므로 바꾸지 않는다.
- 해시가 있지만 `Quota`가 없는 경우(이론상 없음)는 "새로 채움"과 같이 처리한다.

### 4.5 인증 fence·세션 캐시와의 관계

바꾸지 않는다. 이유는 다음과 같다.

- 인증 fence의 수명(`userAuthFenceTTLSeconds` = `SYNC_FREQUENCY` + max(`SYNC_FREQUENCY`, 60))은 "fence 이전에 채워진 해시가 인증에 쓰일 수 있는 기간"보다 길어야 한다.
- 이 설계에서 해시의 인증 정보가 쓰일 수 있는 기간은 `FreshUntil`까지, 즉 마지막 쓰기 뒤 `SYNC_FREQUENCY` 이내다. 지금 해시 TTL과 같은 길이다. 그 뒤에는 반드시 DB를 다시 읽고, fence가 걸려 있으면 지금처럼 거절된다.
- 따라서 해시 자체가 24시간 남아 있어도 fence 규칙은 지금과 같은 조건으로 성립한다.
- 세션 캐시 수명(`userSessionCacheDeadline`)은 `userCacheTTLSeconds()`를 그대로 쓴다. 이 함수는 바꾸지 않고, 잔액 TTL은 새 함수로 둔다.

### 4.6 추천 적립 이전의 캐시 동기화

`TransferAffQuotaToQuota`(`model/user.go`)는 DB 행을 `Save`로 쓰고 캐시는 맞추지 않는다. 지금은 60초 안에 해시가 사라지며 저절로 맞춰지지만, 상주시키면 이전한 금액이 캐시에 계속 반영되지 않는다. 커밋이 성공한 뒤 이전 금액만큼 `cacheIncrUserQuota`를 호출한다. 이 경로는 잔액이 실제보다 적게 보이는 쪽이라 초과 사용 위험은 없지만, 이전한 금액을 바로 쓸 수 없게 된다.

### 4.7 잔액 어긋남 감지 로그

§4.3의 2단계(정보 다시 읽기)에서 DB 잔액과 캐시 잔액을 함께 얻으므로, 둘을 비교한다. 앱 서버는 HA 구성으로 여러 대가 같은 Redis를 쓸 수 있다고 가정한다.

판정 규칙:

1. 이 서버의 배치 큐에 그 사용자의 대기분이 있거나 반영 중(§4.11)이면 비교하지 않는다.
2. 없으면 이번 관찰의 (캐시 잔액, 차이 = 캐시 잔액 − DB 잔액)를 사용자별로 기억한다. 프로세스 메모리에 사용자당 한 쌍만 둔다.
3. 다음 관찰(최소 `SYNC_FREQUENCY` 뒤)에서 캐시 잔액이 그대로이고 차이도 그대로이며 0이 아니면 경고 로그를 남긴다. 사용자 ID, 캐시 잔액, DB 잔액, 차이를 남긴다. 차이가 0이면 기억을 지운다.

근거:

- 잔액 변경은 어느 서버에서 일어나든 공유 캐시를 먼저(차감) 또는 커밋 직후(충전) 바꾼다. 두 관찰 사이에 캐시 잔액이 그대로였다면 그동안 어떤 서버도 잔액을 바꾸지 않았다.
- 이전 관찰 때 다른 서버에 있던 대기분은 배치 간격과 DB 쓰기 시간을 합친 시간(운영 기준 10초 안팎) 안에 반영되며, 반영되면 DB가 바뀌어 차이가 달라진다. 이 시간은 `SYNC_FREQUENCY`보다 짧아야 한다.
- 따라서 캐시와 차이가 모두 그대로인데 0이 아니면, 어느 서버의 대기분으로도 설명되지 않는 어긋남이다.
- 사용 중인 사용자는 캐시 잔액이 바뀌므로 자연히 비교에서 빠진다. 같은 금액의 요청을 반복하는 사용자도 잘못 걸리지 않는다.
- 변경 시각 같은 새 해시 필드는 두지 않는다.

값을 고치지는 않는다(결정 6).

### 4.8 설정과 끄는 법

- 새 환경 변수 `QUOTA_CACHE_TTL`(초). 기본값 86400.
- `QUOTA_CACHE_TTL <= 0`이면 상주를 끈다. 잔액 TTL은 `userCacheTTLSeconds()`가 되고, 차감과 정산에서 TTL을 연장하지 않는다. 즉 upstream 동작으로 돌아간다. 장애 때 되돌리는 스위치다.
- `QUOTA_CACHE_TTL`이 `SYNC_FREQUENCY`보다 작으면 `SYNC_FREQUENCY`를 쓴다.
- `.env.example`과 `docker-compose.yml`에 설명을 추가한다.

### 4.9 운영 절차

캐시를 거치지 않고 DB 잔액을 직접 고친 경우(SQL 콘솔, 일회성 스크립트), 그 사용자의 캐시 해시를 지운다. 다음 요청이 DB에서 새로 읽는다.

```bash
redis-cli DEL user:<사용자 ID>
```

배치가 켜진 환경에서는 그 사용자의 최근 몇 초 사용분이 DB에 반영된 뒤(배치 간격 + DB 쓰기 시간 이후) 지우는 것이 안전하다. 이 절차를 운영 문서에 적는다.

### 4.10 fork overlay 규칙

- 로직은 fork 파일(예: `model/user_quota_residency_fork.go`)에 둔다. 잔액 TTL 함수, 신선 기한 판정, 감지 로그, 바뀐 Lua 스크립트가 여기에 들어간다.
- upstream 파일에는 한 줄 훅만 둔다. 예상 위치는 `model/quota_reserve.go`(사용자 스크립트 두 개의 Eval 호출), `model/user_auth_cache.go`(`writeUserCache` 스크립트 선택), `model/user_cache.go`(읽기 경로의 신선 기한 확인), `model/user.go`(추천 적립 이전 뒤 캐시 동기화), `model/utils.go`(배치 반영 중 표시·재시도·종료 시 비우기), `common/init.go`(환경 변수), 종료 처리 위치(§4.12).
- Lua 스크립트를 upstream 문자열 안에서 고치면 여러 줄 hunk가 생긴다. fork 파일에 바뀐 스크립트를 두고, upstream의 Eval 호출 한 줄을 fork 함수 호출로 바꾸는 쪽을 우선한다. 정확한 방식은 계획에서 정한다.
- 모든 훅을 `docs/fork-overlays.md`에 파일:줄로 기록한다.

### 4.11 배치 반영 중 표시

develop의 `batchUpdate`(`model/utils.go`)는 배치를 시작할 때 큐를 통째로 꺼내므로, DB에 쓰는 동안(운영 기준 3~5초) 그 사용자에게 대기분이 없는 것처럼 보인다. §4.7의 1단계가 이 구간을 건너뛰도록, 꺼낸 사용자 잔액 대기분을 "반영 중" 목록에 옮기고 각 사용자의 행을 DB에 쓴 직후 그 사용자만 목록에서 지운다. 배치 전체가 끝날 때 한꺼번에 지우지 않는다.

### 4.12 DB 반영이 누락되는 경우의 보강

§6의 어긋남 원인 중 "캐시가 맞고 DB가 틀린" 두 경우와 "캐시 반영 실패"를 줄인다. 모두 fork 파일과 한 줄 훅으로 넣는다.

1. **종료 시 배치 비우기:** 서버가 종료 신호를 받으면 배치 큐를 DB에 쓰고 끝낸다. develop에는 이 처리가 없어 재배포마다 최대 배치 간격만큼의 차감분이 DB에서 사라진다. 기존 종료 처리(graceful shutdown)가 있으면 그 안에 훅을 두고, 없으면 `main.go`의 신호 처리에 한 줄을 둔다.
2. **배치 반영 실패 재시도:** 사용자 잔액 행의 DB 쓰기가 실패하면 그 차감분을 버리지 않고 다음 배치 큐에 다시 넣는다. 재시도 중인 사용자는 §4.11의 반영 중 목록에 남는다.
3. **캐시 반영 실패 목록:** 커밋 뒤 캐시에 차이를 더하는 단계가 실패했거나(충전류, 정산), Redis 오류로 사전 차감을 DB에서만 한 경우, 그 사용자 ID를 프로세스 안 목록에 적는다. 배치 주기마다 Redis가 응답하면 목록의 사용자 해시를 지우고 목록에서 뺀다. 다음 요청이 맞는 값인 DB에서 새로 읽는다. 해시를 지우는 순간의 대기분만큼 오차가 날 수 있으므로, 그 사용자에게 대기분이나 반영 중인 분이 없을 때만 지운다.

| 분류 | 경로 | 상주 후 |
|---|---|---|
| 캐시에 차이를 더함 | 사전 차감·정산(`quota_reserve.go`, `IncreaseUserQuota`, `DecreaseUserQuota`), 배치 반영(캐시는 이미 반영), 관리자 잔액 조정(`user_quota_adjustment.go`, 차이만 반영), 결제 충전(`creditTopUpTarget` → `syncCreditUserQuotaCache`), 리딤 코드, 출석 보상, 잔액으로 구독 구매(`cacheDecrUserQuota`) | 문제없음 |
| DB를 고친 뒤 해시를 지움 | 조직 멤버 배정·수정·제거, 소유자 변경, Excel 잔액 가져오기(`SetOrganizationMemberQuota`), 사용자 삭제 | 다음 요청에서 DB를 새로 읽음. 지운 순간의 배치 대기분만큼 오차 가능(§6) |
| 캐시를 맞추지 않음 | 추천 적립 이전(`TransferAffQuotaToQuota`) | §4.6에서 고침 |
| 해당 없음 | 관리자 사용자 수정(`Update`·`Edit`은 `quota`를 `Omit`), 신규 가입(해시 없음) | 문제없음 |

계획의 첫 단계에서 이 표를 다시 확인한다(코드가 바뀌었을 수 있다).

## 6. 남는 한계

- **해시가 지워지는 경우:** Redis 재시작이나 장애 조치, upstream이나 조직 기능이 해시를 지우는 경우, 캐시 스키마 버전이 바뀌는 업그레이드. 그 순간 DB에 반영되지 않은 배치 대기분만큼 초과 사용이 가능하다. 대기분은 배치 간격과 DB 쓰기 시간 동안의 사용량이라 작고, 이런 일은 드물다.
- **API 키 잔액:** API 키 캐시는 바꾸지 않으므로, 잔액 한도가 있는 키는 지금처럼 키 캐시가 60초마다 사라질 때 대기분만큼 초과될 수 있다. 사용자 지갑에서 차감되는 요청은 지갑 차감(`service/funding_source.go`의 `TryReserveUserQuota`)이 따로 일어나므로 지갑 잔액은 이 설계로 지켜진다. 구독 플랜처럼 지갑을 차감하지 않는 요청은 키 한도가 유일한 상한일 수 있고, 그 경우 키 한도 초과가 남는다.
- **직접 DB 수정:** §4.9 절차를 따르지 않으면 어긋남이 남는다. §4.7 로그로 감지한다.
- **배치 반영 실패가 길어지는 경우:** §4.12의 재시도가 계속 실패하면(DB 장애) 캐시는 사용량을 기억하지만 DB는 뒤처진 채로 남는다. 캐시가 맞는 쪽이므로 §4.7 로그가 그 사용자들을 가리킨다. DB가 회복되면 재시도가 반영한다.
- **배치 비활성 환경:** 이 문제가 원래 없다. 상주는 DB 읽기를 조금 줄이는 효과만 있다.
- **비정상 종료:** 프로세스가 강제 종료되면(OOM, SIGKILL) 배치 큐와 §4.12의 캐시 반영 실패 목록이 사라진다. §4.12의 종료 시 비우기는 정상 종료만 다룬다. 큐가 사라지면 캐시가 맞고 DB가 대기분만큼 뒤처지며, 24시간 뒤 해시가 사라질 때 DB 값으로 돌아간다. 지금 develop에도 같은 손실이 있고(60초 뒤 DB 값으로 돌아감), 이 설계가 새로 만드는 문제는 아니다. 사용자가 계속 쓰는 동안은 §4.7 로그에 걸리지 않는다.
- **병합으로 들어오는 새 쓰기 경로:** upstream 병합으로 캐시를 맞추지 않고 `users.quota`만 바꾸는 경로가 들어올 수 있다. 지금은 60초 안에 저절로 맞춰지지만 상주시키면 남는다. §8의 허용 목록 테스트로 병합 직후 드러나게 한다.

## 7. 메모리 추정

필드 수와 값 길이로 추정한 값이다(측정 아님).

| 사용자 수 | 사용자 해시(약 0.6 KB 이하) |
|---|---|
| 1,000 | 약 0.6 MB |
| 10,000 | 약 6 MB |
| 100,000 | 약 60 MB |

24시간 안에 잔액을 쓴 사용자만 남는다. ElastiCache의 가장 작은 노드도 약 0.5 GB다. 기본 eviction 정책(`volatile-lru`)은 TTL이 있는 키만 밀어내며, 이 설계의 해시는 모두 TTL이 있다. 운영에서는 CloudWatch `Evictions`가 0인지 확인한다.

## 8. 테스트

miniredis와 SQLite로 다음을 고정한다.

1. **재현 테스트의 회귀화:** 배치 모드에서 차감 후 `SYNC_FREQUENCY`보다 긴 시간이 지나도(miniredis `FastForward`) 해시가 남아 있고, 배치 반영 뒤 캐시와 DB 잔액이 같다.
2. **신선 기한:** 신선 기한이 지난 해시를 읽으면 DB의 사용자 정보(예: 그룹, 이메일)로 바뀌고, 잔액은 캐시 값 그대로이며, TTL은 연장되지 않는다. 돌려준 `UserBase.Quota`도 캐시 값이다.
3. **TTL 연장:** 사전 차감과 정산 성공 시 TTL이 잔액 TTL로 다시 설정된다. 잔액 부족 거절 시에는 바뀌지 않는다.
4. **비활성 사용자:** 잔액 변화 없이 잔액 TTL이 지나면 해시가 사라지고, 다음 읽기에서 DB 잔액으로 다시 채워진다.
5. **인증 fence:** 기존 fence·세션 테스트가 그대로 통과한다. 추가로, fence가 걸린 동안 신선 기한이 지난 해시는 인증에 쓰이지 않는다.
6. **추천 적립 이전:** 이전 뒤 캐시 잔액이 DB 잔액과 같다.
7. **감지 로그:** 이 서버에 대기분이나 반영 중인 분이 있으면 비교하지 않는다. 캐시 잔액과 차이가 두 관찰에서 그대로이고 0이 아닐 때만 로그가 남고, 캐시 잔액이 바뀌었거나 차이가 바뀌었거나 0이면 남지 않는다.
8. **반영 중 표시:** 배치가 DB에 쓰는 동안 그 사용자는 대기 상태로 보이고, 행을 쓴 직후 풀린다.
9. **종료 시 비우기:** 큐에 대기분이 있는 상태에서 종료 처리를 호출하면 DB에 반영된다.
10. **반영 실패 재시도:** DB 쓰기가 실패한 차감분이 다음 배치에 다시 들어간다.
11. **캐시 반영 실패 목록:** 캐시 반영에 실패한 사용자의 해시가 다음 배치 주기에 지워지고, 다음 읽기에서 DB 값으로 채워진다. 대기분이 있는 동안은 지우지 않는다.
12. **쓰기 경로 허용 목록:** `users.quota`를 바꾸는 코드 위치(파일과 함수)를 허용 목록으로 두고, 소스를 훑어 목록에 없는 쓰기가 있으면 실패하는 fork 테스트. upstream 병합 뒤 새 경로가 들어오면 즉시 드러난다. 목록에 넣을 때 그 경로가 캐시를 맞추는지 확인한다(§5 표 갱신).
13. **끄는 스위치:** `QUOTA_CACHE_TTL=0`이면 TTL이 `SYNC_FREQUENCY`이고 차감에서 연장되지 않는다(지금 동작).

MySQL·PostgreSQL에는 새 SQL이 없다(Redis와 기존 GORM 호출만 쓴다).
